# Clarity Space — аудит безопасности бэкенда

> Репозиторий: `avsmolentsev-tech/kanban` (commit `c4a11de`). Проверено чтением
> кода + живым тестом API двумя аккаунтами. Фокус: изоляция данных между
> пользователями (многопользовательский режим), авторизация, доступ к файлам.
> Пути вида `файл:строка` — в `packages/api/src/`.

## Итог
База в целом сделана правильно: пароли bcrypt, большинство CRUD-роутов и действий
AI-чата **строго скоупятся по `user_id`**, админка закрыта ролью, есть rate-limit
на вход, коды восстановления не раскрывают существование email. Общий защитный
дефолт тоже верный (`userScopeWhere` → `1=0` без пользователя).

**Но** найдено **9 реальных дыр межпользовательской изоляции/доступа**, из них
несколько — без авторизации вообще. Их нужно закрыть **до** приглашения любых
других пользователей. Ниже — по убыванию серьёзности, с готовым направлением фикса.

## 🔴 Критично (утечка/доступ без авторизации)

### 1. Публичная отдача вложений — без авторизации, без владельца, обход пути
`routes/index.ts:41-46` — `GET /v1/documents/attachments/file/:filename`
зарегистрирован **до** `requireAuth`, не проверяет владельца и отдаёт
`sendFile(path.join(attachDir, filename))`. Имена файлов **предсказуемы**:
`${docId}-${Date.now()}` (`documents.ts:190`) и `task-${taskId}-${Date.now()}`
(`tasks.ts:359`), а не «random/unguessable», как написано в комментарии.
- **Эксплойт:** любой без входа скачивает чужие вложения, подобрав имя.
- **Доп. риск:** `filename` не санитизируется → обход пути (`../`) к файлам вне
  папки (`.env`, SQLite).
- **Фикс:** удалить этот публичный роут. Рабочая защищённая версия уже есть в
  `documents.ts:105-113` (проверяет `documents.user_id`) — она сейчас мертва,
  т.к. публичная перехватывает запрос первой. Добавить проверку, что
  `path.resolve` остаётся внутри `attachDir`.

### 2. `email-webhook` — захардкоженный секрет + запись в любой аккаунт
`email-webhook.ts:11` принимает запасной секрет `'pis-webhook-2026'`, зашитый в
код (работает даже без `WEBHOOK_SECRET`). `:22` берёт `user_id` из `?user_id=`/тела.
- **Эксплойт:** зная константу из публичного репо, любой создаёт задачи в **любом**
  аккаунте (`user_id` на выбор).
- **Фикс:** убрать хардкод-секрет; секрет только из env; по возможности привязать
  вебхук к пользователю через персональный токен, а не числовой `user_id`.

### 3. `claude-notes` — весь роут без скоупа
`claude-notes.ts:13,35,48` — таблица `claude_notes` имеет `user_id`, но ни один
запрос по нему не фильтрует.
- **Эксплойт:** любой залогиненный читает (`GET /`, с `content`), правит
  (`PATCH /:id`) и удаляет (`DELETE /:id`) чужие заметки по id.
- **Фикс:** добавить `user_id` во все запросы (из `getUserId(req)`), писать его при
  INSERT.

## 🟠 Высокое (межпользовательский доступ для залогиненных)

### 4. `PATCH /v1/projects/reorder` — запись без владельца
`projects.ts:68-73`: `UPDATE projects SET order_index=$1 WHERE id=$2` — `id` из тела,
без `user_id`. Пользователь B переставляет/ломает порядок проектов A.
**Фикс:** добавить `AND user_id = $…`.

### 5. `GET /v1/ai/search` — чтение чужих задач/встреч + утечка в LLM
`ai.ts:678-689`: `SELECT title FROM tasks WHERE title LIKE ?` и
`SELECT title, summary_raw FROM meetings …` — без `user_id`. Возвращает чужие
заголовки задач и **полные тексты встреч**, да ещё кормит их в Claude.
**Фикс:** добавить `AND user_id = ?` (остальные хендлеры ai.ts скоуплены правильно).

### 6. `GET /v1/ingest/status/:id` — чтение чужого inbox-элемента
`ingest.ts:59` → `ingest.service.ts:~200`: `SELECT * FROM inbox_items WHERE id=$1`
без `user_id`. Список и удаление в этом же файле скоуплены — только статус нет.
**Фикс:** передавать и фильтровать `user_id`.

### 7. OAuth `?uid=` — подмена личности на публичных `/auth`
`google-calendar.ts:37`, `todoist.ts:67`, `yandex-calendar.ts:64`:
`getUserId(req) || Number(req.query['uid'])`. На публичном роутере без JWT доверяет
`?uid=N` и подписывает OAuth-`state` на произвольного пользователя → можно
привязать свой календарь/Todoist к чужому аккаунту. `/callback` проверяет
подпись `state` корректно — проблема только в `uid`-фолбэке.
**Фикс:** убрать `?uid=` фолбэк, требовать реальную авторизацию.

## 🟡 Среднее

### 8. `tags` — глобальная таблица без владельца
`tags.ts:16,22,32`: у таблицы нет `user_id`. `GET` отдаёт теги всех;
`DELETE /:id` удаляет любой тег и каскадит `DELETE FROM task_tags` по **всем**
пользователям. Привязка/отвязка к задаче при этом владельца задачи проверяет.
**Фикс:** добавить `user_id` в `tags` и скоупить список/удаление.

### 9. `tasks` dependencies — чтение чужой задачи через зависимость
`tasks.ts:330-342`: `POST /:id/dependencies` проверяет владельца родителя, но
`depends_on_id` из тела не проверяет; затем `GET /:id/dependencies` возвращает
`title,status,priority` связанной задачи. A добавляет зависимость на задачу B и
читает её поля.
**Фикс:** проверять владельца `depends_on_id` перед вставкой.

## 🔑 Аутентификация и сессии (не IDOR, но важно для мультиюзера)
- **Подтверждение email не форсится.** `auth.ts`: регистрация сразу выдаёт рабочий
  JWT на 30 дней, `email_verified` нигде не проверяется (поиск по коду — только
  запись). Проверка почты сейчас косметическая. **Фикс:** гейтить вход/критичные
  действия по `email_verified`.
- **Токены:** JWT 30 дней, без отзыва; принимается через `?token=` в URL
  (`auth.ts:22-24`) → попадает в логи/Referer; на фронте лежит в `localStorage`
  (крадётся XSS). **Фикс:** httpOnly-cookie + короткий access + refresh, отзыв
  сессий; `?token=` оставить только там, где реально нужно (скачивание файла), и
  узким токеном.
- **Коды** восстановления/подтверждения — 6 цифр на `Math.random()`
  (`email.service.ts:38`), `verify-email`/`reset-password` без персонального
  rate-limit (глобальный `/v1/auth/` 10/мин per-IP смягчает, но distributed обходит).
  **Фикс:** `crypto.randomInt`, счётчик попыток на код, инвалидация после N неудач.
- **Пароль** — минимум 6. **Фикс:** поднять до 8–10 + проверка на простые.
